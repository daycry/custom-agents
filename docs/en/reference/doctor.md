# `/doctor`: reference notes

> English mirror of [`agent-kits/shared/doctor-reference.md`](../../../agent-kits/shared/doctor-reference.md) (the notes live there so they travel with the kit to every runtime), condensed. `commands/doctor.md` only keeps a summary of the symbols and points to the original note (`$R/agent-kits/shared/doctor-reference.md`), so these notes are not loaded on every invocation (audit H-44). The diagnosis is computed by `agent-kits/shared/doctor.py`; these notes explain how to read it.

## Notes

- **What each symbol means**: ✅ correct · ⚠️ works but half-way (opt-in half configured, unverified token price, non-executable hook) · ❌ broken (corrupt config, value outside its vocabulary, missing script) · ℹ️ informational (optional piece not installed, opt-in deliberately off, work state). ℹ️ rows **do not** need fixing.
- **How it is installed**, not only whether the files exist: the «Plugin» block tells a **plugin** (registered in `installed_plugins.json` / `enabledPlugins`, or rooted under `<CLAUDE_CONFIG_DIR>/plugins/cache/`) from a **copy** (the bundle in `.claude/`, routes 1 and 2 of `docs/INSTALL.md`). In copy mode «hooks registered» is ⚠️ however complete `hooks/hooks.json` is: **Claude Code does not read it outside an installed plugin**, so there are no hooks, no statusline and no `/custom-agents:` namespace; the fix is `npx @daycry/custom-agents install -p claude-code`. The «plugin registry» row says in which file and scope it is registered and is ❌ if `enabledPlugins` has it `false`. The same per runtime from outside a session: `npx @daycry/custom-agents status`.
- **Active, not «noted somewhere»**: the verdict comes from the EFFECTIVE state for THIS folder: only the exact plugin key counts (a `custom-agents@<other>` does not), `project` or `local` scope entries count only if they belong to this project, and an explicit `false` at the winning level beats any registration. `enabledPlugins` is read in the **four** files of the documented stack, in precedence order: platform `managed-settings.json` > `.claude/settings.local.json` > `.claude/settings.json` > the `settings.json` of your `CLAUDE_CONFIG_DIR`. The row **names the winning file**, which is where to edit. An installed but disabled plugin is `inactivo` and its hooks cannot be ✅. `status` resolves the same state with the same rules: the two tools cannot contradict each other.
- **The three runtimes**: besides Claude Code there is a row for «registry in Codex» (`enabled = true` in the scope's `config.toml`) and «registry in OpenCode» (the hooks adapter under `plugin` in `opencode.json`). If that runtime is not on the machine the row is ℹ️ and asks for nothing.
- **How the command is typed** (gap E5): the «command names» row gives the form that works in THIS installation, with **three** texts by detected mode, always ℹ️. `plugin` → the real name carries the namespace, `/custom-agents:<cmd>`, and the short form gives «Unknown command». `copia` → short form `/<cmd>`, with a warning that `/custom-agents:<cmd>` only exists as an installed plugin. `inactivo`/`desconocido` → **both** forms with their condition. If `plugin_root` has no `commands/` folder the row says so and names no command. The namespace belongs to **Claude Code**: in Codex the same command is a `/<cmd>` prompt and in OpenCode an unprefixed command. The ⚠️ «live doc without the namespace» fires only if the **first** mention of a command in a **live** documentation file (`README.md`, `README.es.md`, `docs/INSTALL.md`, `docs/README.md`, their `docs/en/` mirrors and `CLAUDE.md`) uses the short form. Dated records (`docs/roadmap/`, `docs/knowledge/`, CHANGELOG) are not inspected.
- **Eight blocks**: tools · plugin and hooks · statusline · `.claude/` configs · work state · **optional capabilities** (`agent-kits/shared/capabilities.py`, CA-14 of knowledge-services: one row per registered capability, with NO per-capability code; invalid config → ❌ with file, field and fix; disabled → ℹ️ and **omitted** if its `config_path` does not exist unless `--verbose`/`--all`; active with a declared backend → a LIVE check through ITS adapter: ✅ healthy, ⚠️ stale export with the remedy `verify()` names [never run], ⚠️ incomplete verification, ⚠️ healthy with warning, ⚠️/❌ degraded/error, ℹ️ offline or timeout; `graphiti` reports `off`/`shadow`/`read` by its `mode`, `training` adds the case-store root, counts by state read from `cases/`, incomplete versions, orphan temporaries, files over 1 MiB and dataset freshness; bounded to 2 s and declared **PARTIAL** when it cannot walk everything: `dataset-assembler.py --estado` verifies without a cap; the budget only trims capabilities that need network, so a configuration ❌ is never lost) · **technical memory** (`docs/knowledge/`: curated entries by family and state, README index —❌ if the bijection breaks—, FTS5 index, journal at 0 with curated memory, stale `CALIBRATION.md` with closed initiatives without a retro) · **Journal** (`journal.py status --json`: outbox/processing/done/dead-letter counters, orphans, pending backoff with the remedy named, and triage of «Hook cancelled»: runtime notice without loss vs possible loss).
- **Automations: configuration, not execution.** Outside the eight blocks (they do not add to ✅/⚠️/❌ nor change the exit code), the «Automatizaciones» section and the `automatizaciones` key of `--json` list every hook of `hooks/hooks.json`, the `statusLine` of project, local and user settings, and each workflow of `.github/workflows/` (up to 20). Each row carries `fuente`, `alcance`, `fecha_fuente` (when the config changed, not when it ran), `estado` (`configurado` · `no_configurado` · `no_cargado` · `roto` with its `firma_fallo`) and `ejecucion: no_verificada`: `/doctor` neither observes dispatches nor queries remote CI, so do not present any row as «working».
- **The plugin version check is offline by design**: `/doctor` does not query the marketplace, so it cannot say whether a newer plugin version exists; it reports the installed one. (This is NOT a general «no network» claim: optional capabilities enabled in `taxonomy.json` do a bounded live check against local/private hosts under a total time cap.)
- **Do not confuse with `/setup`**: `/doctor` diagnoses what is there (read-only); `/setup` configures and writes (`rates.json`, `dev.json`, Jira/Confluence opt-ins, statusline).

## Graph memory (`graphiti`), if the project declares it

An **optional capability like any other** in the registry (`capabilities.py`), like `kwipu`: `/doctor` carries no code of its own for it (CA-14 of knowledge-services; the string `graphiti` does not appear in `agent-kits/shared/doctor.py`). In the «Optional capabilities» block you will see:

| Row | Meaning | What to do |
|---|---|---|
| `graphiti: deshabilitado` | No backend `type: graphiti` with `enabled: true` in `taxonomy.json` | nothing; enable it with `/setup` if you want it |
| `graphiti: … en off` | Declared but off by configuration (`mode: off`): neither syncs nor reads | set `mode: "shadow"` to start syncing |
| `graphiti: … en shadow` | Syncs and **never** reads: the router never queries the graph in `shadow` (CA-10) | when `--check` shows no drift, move to `mode: "read"` |
| `graphiti: … en read` | Routed reading active: `knowledge-find.py --intent <intent>` may be served by the graph if that intent is in `router.intents` | check the `graphiti (backend)` row |
| `graphiti: … en degradado` | Enabled but with incomplete or invalid configuration | fix the field the row itself names in `taxonomy.json` |

The `graphiti (backend)` row is the **live** network check the adapter does (`health()` + `verify()`), under the same time cap as any other capability and always against the declared **local** endpoint. `/doctor` registers no MCP server and touches no global configuration: it only reads.

`/doctor` trims the adapter read window to **200 entries** (it is a diagnosis, not an exhaustive verification). Two different rows come out of that:

- **ℹ️ «verification bounded to 200 of N entries by /doctor»**: the manifest has more entries than that window, so the cut is `/doctor`'s, not a backend problem. A drift OUTSIDE the window is not visible from here; the full verification is `python skills/knowledge-services/scripts/knowledge-sync.py --backend <id> --check`.
- **⚠️ «incomplete verification: N entries unconfirmed»**: the manifest DID fit the window and the adapter still could not confirm it all; the limit is its own read cap. It is not drift: it could not be looked at, so it does not authorize routed reading either (CA-10).

And a third case: **ℹ️ «verification not available: …»** when the adapter answers `no_verificable` (backend in `mode: off`, no endpoint, unreadable response); the row carries its `razon`.
